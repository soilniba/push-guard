# 设计决策：审查前由用户选择，放弃是允许的结局

## 问题

原规则下 hook 拦住未审查的 push 后，直接用拦截信息让模型去跑
`push-guard:pre-push-review`。于是审查是自动开始的：大 diff 还要额外起独立
reviewer 子代理。用户没有机会说"这次不推了"，只能为一次自己并不想要的 push
付掉整轮审查成本。

## 决策

1. 未审查的 push 仍然拦住——"未审查不推送"这条不变。
2. 拦截信息改为指令模型先用 `AskUserQuestion` 问用户：
   - 进行审查并推送 → 跑 skill，通过审计后重试 push
   - 放弃本次 push → 停止，提交留在本地
3. 不提供"跳过审查直接推送"的出口（见下）。

## 为什么不用 hook 的 `permissionDecision: "ask"`

`ask` 会让 Claude Code 弹出原生权限确认框，点击来自 harness、模型无法伪造，
看起来是更"正规"的用户选择通道。但它只有允许/拒绝两态，且"允许"= 放行这次
Bash 调用 = 未审查直接推送。也就是说，要给出"跳过审查"的出口，就必须给闸门
开一个一键绕过。保住"未审查绝不推送"，拦截只能是 `deny`。

另外 Codex 侧没有等价的 `ask` 能力（其 PreToolUse 只有 `allow`/`deny`），
`deny` + 让模型自己问是两端行为一致的做法。

还有第四个取值 `defer`——非交互模式（`claude -p`）下把问题交给外层 UI。那要求
调用方自绘界面，插件形态用不上。非交互场景问不出用户时，模型停在"未推送"，
方向是安全的（等同于放弃）。

## 补充（2026-09-10）：决定"不再自动"的地方不止拦截信息

拦截信息只回答"被拦下之后怎么办"。决定审查会不会**自己开始**的是另一处：skill 的
frontmatter description。它当时仍是 `Use before every git push or PR creation…`，
模型每轮都能看到，于是在 push 之前就把 skill 调起来——审查在 hook 之前就开始了，
拦截信息根本没机会出现。本次把 description 改成"仅在闸门拦下且用户选择审查后使用"。

仍未关闭的口子：模型可以无视拦截信息直接去跑审查。description 收口后，这需要模型
主动违背一条显式指令，概率大幅下降，但没有机制保证。要真正关闭，得让审计强制要求
会话里存在一次真实的 `AskUserQuestion` 记录（模型伪造不了），代价是非交互模式
（`claude -p`）下永远推不出去。

## 代价

审查不再自动开始，每次 push 多一次交互（同一次 push 的重试不再重复询问，
否则审计每失败一轮就把用户重问一遍）。这是需求本身要的取舍：省掉的正是
"用户根本不想要的那次 push"所附带的审查成本。副作用是模型可以无视拦截信息
直接去跑审查——那退化成旧行为，闸门不受影响，只是少问了一次。
