# 设计决策：判定不出"是不是 push"时一律拦住

## 问题

阶段 1 用 python3 解析 hook 输入并判断命令是不是 push。python3 缺失或解析失败时
它输出为空，而空输出被当作"不是 push"处理 → 直接放行。闸门在最需要它的环境里
（依赖缺失、环境异常）恰好失效，方向是错的。

## 决策

阶段 1 没有给出结论时，宁可拦住：

1. 区分"读不出命令"与"不是 push"两种结果。读不出时输出 `__UNPARSED__`，
   不再冒充 `__NO_PUSH__`。
2. 阶段 1 结果为空或 `__UNPARSED__` 时，用 bash 内置正则直接扫原始输入；
   命中 push 形态就 deny，并说明是环境问题而非审查结论。
3. 审计阶段输出为空（脚本整体静默死亡）时，reason 写明"hook 内部故障"，
   不让拦截信息变成一句空白。

## 为什么降级判断用 bash 内置正则

第一版降级判断用 `grep -E`，测试时发现：`grep` 同样可能不在 PATH 上，那样这次
兜底自己又变成一个新的放行口——同一个根因换个工具再犯一次。改用 bash 的 `=~`
ERE 引擎，没有外部进程、没有 PATH 依赖，兜底不会因为环境残缺而失效。

## 代价

正则只看文本，不做 shlex 分词，因此会过拦一部分"看起来像 push"的散文命令
（例如提交信息里字面写着 `git push`）。降级模式本身就是异常状态，多拦几次
（拦截信息会说明是 python3 缺失）比漏放一次好。

已知边界：输入完全为空时仍放行——此时 hook 没有任何信息可判，拦住等于让每次
Bash 调用都失败，代价大于收益。
